# MCP Dock 第三阶段：审批执行 Core

## 当前交付边界

本阶段实现**计划申请 → 本机 CLI 人工确认 → 短时一次性票据 → 执行方核销授权 → 审计留痕**的基础设施。

**不包含实际删除、移动、Git 写入或 Runner 启停执行器。** 消费票据只记录授权被使用，固定返回 `executionPerformed=false`。

## 架构

```text
Codex / Agent（仅受限 MCP 工具）
      |
      +-- request_cleanup_approval
      |      +-- 验证允许的 rootId / 相对路径 / 候选分类
      |      +-- 限额扫描并计算目录元数据快照 SHA-256
      |      +-- 写签名计划、不可变摘要、提案审计
      |      +-- 返回 planId（无审批票据）
      |
      +-- get_cleanup_approval_status
             +-- 读取签名计划与当前状态（不返回票据）

用户独立打开 Windows 本地终端
      |
      +-- npm run approval -- show <planId>
      +-- npm run approval -- approve <planId>
      |      +-- 必须交互式 TTY，并手动输入 APPROVE <前 8 位>
      |      +-- 重新计算资源快照并比对
      |      +-- 签发 10 分钟的一次性敏感票据
      +-- npm run approval -- reject <planId>
             +-- 必须交互式 TTY 手动确认

后续受控执行器（尚未开放）
      |
      +-- ApprovalService.consumeTicket(ticket, expectedOperation)
             +-- 核对操作、路径、计划摘要、资源版本、有效期
             +-- 目录快照二次检查、进程间互斥、防重放
             +-- 原子写入一次性核销记录并记录审计
             +-- 仅返回授权凭据，当前不执行目标操作
```

## 使用方法

在仓库根目录执行以下命令：

```powershell
npm run build
npm run approval -- list
npm run approval -- show <planId>
npm run approval -- audit <planId>
npm run approval -- approve <planId>
npm run approval -- reject <planId>
```

`approve` / `reject` 不支持 `--yes`、`--force` 或标准输入管道自动确认。审批时会显示目标路径、资源版本、文件数量和估算字节数，需要用户在独立交互式终端输入指定确认文本。

审批票据只在批准成功时输出一次，不写入审计或可查询状态，也不通过 MCP 返回。用户应当将其视为短期敏感凭据。

## 当前允许申请的操作

仅支持 `cleanup-directory`（**提出清理目录的意图，不执行清理**）。

- 只能使用 `config/system-mcp.yaml` 中登记的目录根和相对路径。
- 目标名称必须属于固定缓存/构建目录白名单（例如 `dist`、`build`、`target`、`node_modules`、`.gradle`、`__pycache__`）。
- 禁止登记根本身、任意非候选路径、目录穿越、符号链接和常见敏感路径。
- 快照扫描最多 10,000 个条目、目录深度最多 16；超预算直接拒绝，不提供不完整计划。
- 资源版本基于路径及文件/目录元数据（大小、修改时间、创建或变更时间、模式、inode）形成摘要，**并非文件内容哈希，也不能代替未来执行器的安全复核**。

## 状态和过期

| 状态 | 含义 |
|---|---|
| `pending` | 计划尚未被人工批准/拒绝 |
| `approved` | 已签发票据，仍在有效期内，尚未核销 |
| `rejected` | 人工拒绝 |
| `consumed` | 授权票据已核销，不能重复使用 |
| `expired` | 计划或票据过期，不能继续批准或核销 |

计划最长有效期 60 分钟，票据最长有效期 10 分钟（且不超过计划到期时间）。同一计划只能批准或拒绝一次；需要重新批准时应创建新计划并重新核查目标。

## 本地状态与审计

本地状态目录：`.local/approval/`（Git 已忽略）。

- `secret.key`：用于计划、票据元信息和审计记录的本地 HMAC 密钥，不提交到 Git。
- `plans/`：计划、固定摘要和签名。
- `grants/`：签发元信息与票据 SHA-256 摘要，不存储明文票据。
- `rejections/`：拒绝记录。
- `consumed/`：一次性核销标记，使用独占创建和计划级锁。
- `audit/`：追加式 JSONL 审计，包含前一个事件的哈希与每条 HMAC 签名。
- `locks/`：按计划 ID 建立的互斥锁目录。异常中断遗留锁时故障关闭，不会自动绕过。

审批链不通过 MCP 暴露签发或核销接口；审批客户端不具备任意命令执行能力。

## 安全边界和已知限制

1. 独立 CLI + TTY 是避免**仅持有本 MCP 工具权限的 Agent**直接批准的边界，**并非**对可以执行任意本地命令或控制同一 Windows 用户会话的恶意程序提供强身份认证；同权限进程仍可能接触本地状态与密钥。未来正式执行破坏性操作前，需要结合 Windows 用户隔离、权限分离或 Windows Hello 等独立用户认证机制。
2. 元数据快照不能保证发现相同大小、相同元数据的恶意内容替换，也无法消除文件系统并发变更带来的 TOCTOU 风险；因此当前**不开放任何破坏性执行器**。
3. 审计记录带 HMAC 链式校验，可以检测记录被直接修改，但不能单独抵抗掌握本地签名密钥的同用户攻击者；也不能证明完全删除日志尾部的行为未发生。正式高安全场景需要外部锚点或受保护的日志接收端。
4. 签发后若异常退出，部分记录可能已经落盘但审计未完成；程序将按失败关闭处理，不应自动重试审批。
5. 测试全部使用临时目录；不会对用户真实缓存、项目源码、Git 仓库或 Runner 执行写操作。
